| 2XX 响应 | 10 (0.20%) |
| 4XX 响应 | 4,990 (99.80%) |

- 低并发下性能稳定
- 平均响应时间约 59ms，性能良好
- 99分位响应时间约 73ms，响应时间分布集中
- 大部分 4XX 错误是由于无效的登录凭证（测试数据）

## 测试场景 3: 高并发极限压测
**配置参数:**

- 线程数: 32
- 总请求数: 20,000

**测试结果:**
| 指标 | 数值 |

| 总耗时 | 6.46s |
| 平均响应时间 | 136.58ms |
| 吞吐量 (RPS) | 3,094.05 req/s |
| 中位数响应时间 | 35.88ms |
| 99分位响应时间 | 1,446.64ms |
| 最慢响应时间 | 2,155.00ms |

**分析:**

- 系统在 500 并发连接下开始出现压力
- 部分请求超时或连接被拒绝

## 性能总结

### 性能指标
| 并发数 | RPS | 平均响应时间 | 99分位响应时间 | 错误率 |
|--------|-----|------------|--------------|--------|
| 50 | 838.28 | 58.60ms | 73.16ms | 0% |
| 200 | 779.16 | 249.54ms | 308.86ms | 0% |
| 500 | 3,094.05 | 136.58ms | 1,446.64ms | 89.44% |

### 建议

**1. 性能基线**
- 在 50-200 并发下，系统表现稳定
- 建议单机容纳 **500-1000 RPS** 作为参考基线
- 平均响应时间控制在 **60-250ms**

**2. 容量规划**
- 使用 Docker Swarm 或 Kubernetes 多副本部署
- 在 Nginx 或负载均衡器上配置反向代理
- 推荐副本数: 3-5 个实例

**3. 优化方向**
- 优化登录业务逻辑（数据库查询、密码验证等）
- 配置 Redis 缓存加速热点数据
- 增加连接池大小（MySQL、Redis、Kafka）
- 考虑使用消息队列异步处理非关键操作
- 监控系统资源使用（CPU、内存、网络）

**4. 高可用方案**
- 部署多个应用实例
- 配置数据库主从或集群
- 使用 Redis Cluster 高可用
- 配置 Kafka 多副本因子

---

## 测试结论

✅ **低并发表现优秀**: 50-200 并发下系统运行稳定，无错误  
⚠️ **高并发压力**: 500 并发出现大量错误，系统需要水平扩展  
📊 **吞吐量**: 最高可达 3000+ RPS（高错误率下）  
🎯 **推荐QPS**: 800-1000 req/s 单机性能稳定区间
