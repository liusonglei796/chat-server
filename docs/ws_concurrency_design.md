# WebSocket 并发与资源释放设计 (cleanup)

本文档说明了项目在 `ws_gateway.go` 中通过 `cleanup` 函数管理 WebSocket 连接生命周期的并发设计。

## 1. 设计背景
WebSocket 是一种长连接，由两个 Goroutine（Read 和 Write）共同维护。当连接断开时，必须确保资源（连接、通道、Broker 注册信息）被**完整**且**仅一次**地释放。

## 2. 两个关键触发场景

在实际运行中，有两种完全不同的路径会触发连接的销毁：

### 路径 A：`Read()` 协程退出 (被动断开)
这是由底层的网络状态或协议事件触发的。
- **场景**：
    - **网络异常**：用户进入信号盲区或拔掉网线，`Conn.ReadMessage()` 报错。
    - **心跳超时**：超过 `pongWait` 时间未收到客户端的 Pong 响应（触发 `ReadDeadline`）。
    - **浏览器关闭**：用户关闭了网页或 App 进程，发送了 Close 帧。
- **调用方式**：通过 `Read()` 函数末尾的 `defer c.cleanup()` 触发。

### 路径 B：`ClientLogout` / `KickClient` (主动/逻辑销毁)
这是由外部业务逻辑主动触发的。
- **场景**：
    - **主动登出**：用户在 UI 上点击了“退出登录”，后端接收到注销请求。
    - **账户顶号**：用户在另一台设备登录，系统自动将当前连接踢下线。
- **调用方式**：外部函数通过 `broker` 获取 `UserConn` 实例，并直接调用其 `cleanup()` 方法。

---

## 3. 并发冲突与风险

由于网络环境的复杂性，上述两条路径极有可能**同时触发**。例如：用户点击了退出登录，而与此同时网络刚好抖动断开了，或者用户点完退出瞬间关掉了浏览器。

如果没有并发保护，可能导致以下风险：
1. **二次关闭 Channel (Panic)**：尝试对已经关闭的 `SendBack` 通道再次调用 `close()`，会导致程序崩溃。
2. **连接重复关闭**：导致产生重复且带有误导性的警告日志。
3. **数据竞态**：Broker 内部的映射表清理可能发生冲突。

---

## 4. 解决方案：`sync.Once` 幂等性保障

代码中使用了 `sync.Once` 来封装销毁逻辑：

```go
func (c *UserConn) cleanup() {
    c.cleanupOnce.Do(func() {
        // 1. 从 broker 注销（防止新消息再写进来）
        c.broker.UnregisterClient(c)
        
        // 2. 安全关闭 SendBack 通道（让 Write 协程退出）
        safeCloseMessageBackChan(c.SendBack)
        
        // 3. 关闭网络连接
        c.Conn.Close()
    })
}
```

### 为什么这样做？
- **天然幂等**：无论 `cleanup` 被调用多少次，无论是在哪个 Goroutine 里调用的，内部的代码块**只会执行第一次**。
- **简单高效**：不需要复杂的互斥锁 (`Mutex`) 标记状态，减少了死锁的可能性。
- **安全解耦**：允许业务逻辑和底层驱动独立管理生命周期，互不干扰。
