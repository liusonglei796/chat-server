## 2. 需求背景与业务目标

### 2.1 需求背景（Background）
随着 Kama 平台用户量增长，现有的单向异步通知已无法满足用户高频实时的社交协同需求。用户需要一套轻量、稳定、低延迟的即时通讯（IM）系统，支持随时发起单聊与群组沟通、查看历史会话及安全撤回错误信息。

### 2.2 核心痛点（Pain Points）
1. **弱网与断线感知差**：用户在地铁、电梯等弱网场景下发送消息经常转圈无响应，甚至重复发送多条相同内容。
2. **多端状态不一致**：移动端和 Web 端同时登录时，会话置顶状态、未读消息与撤回状态无法实时同步。
3. **关键信息误发风险**：缺少撤回能力，导致敏感数据或错发信息无法挽回。

### 2.3 业务与体验目标（OKRs / KPIs）
* **稳定性目标**：消息发送端到端延时（P95）< 200ms；实时在线投递率 > 99.9%。
* **体验目标**：消息发送支持“乐观上屏”（发送即显示，失败再提示重试），网络断开 5s 内自动重连并增量同步，不发生消息乱序与丢失。
* **业务目标**：上线后提升活跃用户次日留存率 5%，单用户日均发送消息数提升 20%。

## 3. 用户画像与核心用例场景

### 3.1 目标用户画像
* **场景 A（即时沟通者 Alice）**：日常与好友保持高频交流，要求发消息即刻得到反馈，对断线重发、发错撤回有强烈刚需。
* **场景 B（群组协同者 Bob）**：加入多个技术/兴趣讨论群，消息流极度密集，需要清爽的会话列表排序、置顶核心群聊、清晰的历史翻页体验。

### 3.2 典型用户故事（User Stories）
1. **作为发送方**，我希望在点击发送后瞬间看到消息出现在聊天气泡中，若网络断开能看到红色感叹号并可一键重试，以便我确认消息是否真正到达。
2. **作为接收方**，我希望只要我在聊天窗口内，新消息能自动流式插入底部；当我不在该窗口时，左侧会话列表能显示最新摘要和未读红点。
3. **作为误发者**，我希望在发送 2 分钟内长按/右键撤回该消息，使对方窗口同步替换为“XX 撤回了一条消息”，避免社交尴尬与信息泄露。

## 6. 核心功能详细需求规范

### 6.1 会话列表与聚合管理 (Session Management)

#### 6.1.1 业务规则
1. **会话唯一性规则**：
   * 单聊会话：以两用户 ID 升序排列唯一标识，格式为 `P_{min(A,B)}_{max(A,B)}`。无论 A 先发还是 B 先发，均映射为同一会话实体。
   * 群聊会话：直接以 `groupId` 为会话 ID。
2. **读模型隔离规则**：
   * 会话列表对用户本人保持私有视图。A 删除了与 B 的会话，不影响 B 的会话列表。
3. **置顶规则**：
   * 会话可置顶（`is_pinned = true`）。
   * 排序规则：置顶会话固定在列表顶部，多个置顶会话按其最新消息时间（`last_message_at`）倒序排序；普通会话排在所有置顶会话下方，同样按最新消息时间倒序。
4. **最后消息摘要渲染规则**：
   * 文本消息：直接显示前 30 个字符，超出省略；
   * 文件消息：统一显示文案 `[文件] xxx.pdf`；
   * 撤回消息：显示文案 `对方撤回了一条消息` 或 `你撤回了一条消息`。

#### 6.1.2 交互与异常分支
* **空状态**：若用户无任何会话，列表居中展示插画及文案“暂无聊天消息，去好友列表打个招呼吧”。
* **删除会话**：右键点击“删除会话”，弹出确认弹窗“仅从当前列表中移除，产生新消息时将重新显示”。确定后本地瞬间移除该项。

---

### 6.2 消息发送与交互体验 (Message Sending)

#### 6.2.1 业务规则
1. **消息类型支持**：
   * **文本消息 (`type = 1`)**：支持 1 ~ 4000 个字符。纯空格不可点击发送。
   * **文件消息 (`type = 2`)**：支持常见文档/图片，单文件体积上限 50MB。客户端先完成对象存储上传拿到安全下载 URL 与元数据（文件名、扩展名、体积），再提交消息服务保存。
2. **防重与幂等性保障**：
   * 客户端每次生成唯一的 UUID（`client_msg_id`）。
   * 若同一 `client_msg_id` 在 10 秒内重复提交，服务端禁止产生第二条落库记录，必须返回第一次落库成功的同名消息对象，防止网络抖动造成双发。
3. **关系合法性校验**：
   * 单聊前置校验：若双方已解除好友关系或处于拉黑名单中，服务端拦截并返回错误码：
     * 若被拉黑：前端直接在聊天流中以灰色居中小字呈现“消息已发出，但被对方拒收了”。
     * 若已非好友：以灰色小字呈现“对方开启了好友验证，[发送好友申请]”。

#### 6.2.2 乐观更新（Optimistic UI）交互规范
* 用户点击发送或敲击回车瞬间：
  1. 输入框立即清空，光标复位；
  2. 消息立即追加到消息流最下方，气泡右侧显示轻量旋转 Loading 动画；
  3. 后端在 3000ms 内成功返回时，隐藏 Loading 动画，更新消息正式服务端时间与 ID；
  4. 若超过 8000ms 或 HTTP 返回 5xx/网络断开，Loading 动画替换为红色感叹号图标；
  5. 点击红色感叹号，弹出悬浮菜单：`[重新发送]`、`[删除]`。

---

### 6.3 历史消息加载与游标分页 (Message History & Sync)

#### 6.3.1 业务规则
1. **基于游标（Cursor）的分页机制**：
   * 禁止使用基于页码（Offset/Limit）的传统分页，以规避“翻页过程中产生新消息导致重复展示或跳页”的问题。
   * 游标依据：采用单调自增的主键 `id` 或局部递增 `seq_id`。
   * 每次向上滑动至顶部时，携带当前页面顶部的最老一条消息 `id`（`before_id`），每次最多请求 20 条。
2. **断网重连与增量补齐（Incremental Sync）**：
   * 客户端因后台挂起或网络抖动重连 WebSocket 成功后，自动触发增量检查：
     * 上报客户端当前本地最大的 `max_seq_id`；
     * 服务端补发大于该 `seq_id` 的所有新消息，确保无一遗漏。

#### 6.3.2 页面交互细节
* 向上滚动加载历史时，**绝对禁止**屏幕内容发生剧烈跳动（Scroll Jumps）。前端必须计算加载前后 DOM 元素高度差，锁定当前可视区域。
* 当拉取到最后一条（无更早历史）时，消息顶部显示“—— 已经没有更多历史消息了 ——”。

---

### 6.4 消息撤回机制 (Message Recall)

#### 6.4.1 业务规则
1. **时间窗口限制**：
   * 仅允许消息发送者本人在发送成功后的 **120 秒（2 分钟）** 内发起撤回。
   * 超过 120 秒的服务端请求将被硬性拒绝（返回状态码 `ERR_RECALL_TIMEOUT: 消息超过2分钟无法撤回`）。
2. **多端状态终态化**：
   * 服务端接收到合法撤回请求后，将对应消息的内容字段覆写置空，并将 `type` 更新为系统撤回标识（`type = 4`）。
   * 触发长连接事件，向会话中所有在线成员广播撤回通知。
3. **客户端显示规则**：
   * 发送者本人客户端：原消息气泡替换为灰底居中提示：“你撤回了一条消息 [重新编辑]”（点击重新编辑可将撤回前的文字重新回填入输入框）。
   * 接收者客户端：原消息气泡替换为灰底居中提示：“对方撤回了一条消息”。
   * 若对方当前未在线，下次打开会话拉取历史时，该消息直接作为撤回提示条呈现，原内容不再展示。

## 9. 验收标准与发布检查清单 (Definition of Done)

### 9.1 核心功能验收用例（Acceptance Criteria）
1. [ ] **快速连发场景**：快速连续点击发送 5 条不同文本消息，界面按点击顺序依次乐观上屏，并按严格自增 Seq 排列，无颠倒。
2. [ ] **离线/弱网场景**：拔掉网线或开启浏览器 Network Throttling 发送消息，客户端在 8 秒后正确展示红色失败感叹号；恢复网络后点击感叹号可成功补发。
3. [ ] **2分钟撤回边界**：
   * 发送后第 1 分 50 秒发起撤回 -> 提示撤回成功，双方窗口实时变为撤回灰条。
   * 发送后第 2 分 05 秒右键 -> 撤回菜单已灰显置灰，若通过接口强刷撤回，服务端返回超期失败提示。
4. [ ] **幂等防重拦截**：抓包重放包含相同 `client_msg_id` 的请求，服务端不新增数据，返回首次响应。

## 10. 附录：产品经理设计决策思考（PM 批注）

* **【为什么单聊 session_id 必须强制归一化？】**  
  * *背景*：如果 User A 和 User B 聊天，A 端发起时如果叫 `chat_A_B`，B 端发起时如果叫 `chat_B_A`，就会在数据库产生两条平行会话，导致两端消息无法聚合。  
  * *PM 决策*：无论谁发消息，底层统一按照 `min(A,B) + "_" + max(A,B)` 映射，彻底在产品根源上规避“双向平行宇宙”。
* **【为什么撤回时效卡死在 2 分钟，且要清除数据库内容？】**  
  * *体验权衡*：时间太短（如 30 秒）用户来不及发现错别字；时间太长（如 10 分钟）接收方已经阅读并形成心理预期，被撤回会产生极大的沟通欺骗感和断裂感。微信的 2 分钟正是人类社交容错与信息确定性的黄金平衡点。  
  * *合规与隐私*：撤回时不仅前端不展示，后端数据库必须清空正文内容，规避误发密码或隐私数据留存在库中的合规风险。
