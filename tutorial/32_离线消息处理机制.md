# 离线消息处理机制

本文档详细介绍了当前系统中离线消息的处理机制。整体上，系统采用 **“先存储后推送、客户端上线主动拉取”** 的核心模式。

---

## 1. 整体处理流程

在目前的系统架构（基于 `MsgConsumer` 和 Kafka 集成）下，离线消息不会在服务端造成阻塞，而是通过持久化和缓存保障数据的完整性与高可用。具体的处理流转如下：

### 1.1 无差别持久化（先存储）
无论接收方在线与否（单聊或群聊），当 `MsgConsumer` 从 Kafka 消费到一条新消息时，将在第一时间做持久化处理：
- 调用 `persistMessage(&message)` 将该消息持久化保存到 MySQL 数据库中（`message` 表）。
- 异步更新关联的会话层信息（使用 `updateSessionLastMessage` 更新 `Session` 表中的最后一条消息记录）。
这些操作与客户端状态解耦，确保消息数据绝对安全、不丢失。

### 1.2 检查在线状态与静默路由
在进入 `dispatchToUser` (单聊) 或 `dispatchToGroup` (群聊) 路由分发阶段：
服务端会在内存中的在线用户映射表（如 `MsgConsumer.Clients` 这个 `sync.Map` 结构）里查找接收方是否维护了活跃的 `UserConn` (WebSocket 连接)。

- **若用户在线**：会匹配到对应的连接，将消息放入该用户的 `SendBack` channel，触发 WebSocket 的实时推送。
- **若用户离线**：内存映射表中会寻找失败，此时系统直接**静默跳过 WebSocket 推送过程**，不会引发任何错误。同时，依然会执行后续的异步缓存更新，将这条消息追加保存到 Redis 的聊天记录列表中（通过 `constants.CacheKeyMessageList...` 相关的 key），保证了 Redis 缓存的数据一致性。

### 1.3 客户端上线主动拉取 (Pull 机制)
因为离线期发给该用户的消息都已经安全地降落在了 MySQL 中，并且大概率已被预热在 Redis 缓存里：
当离线用户重新启动 App、或者网络重连成功后，客户端需要调用“获取历史消息列表”的 HTTP 拉取接口 (如 `GetMessageList`)，向服务器请求离线期间积攒的数据。
通过比对本地最后一条消息的 ID 或时间戳，客户端能够把所有的离线消息完整同步到本地，完成真正的离线消息送达。

---

## 2. 机制设计总结

- **高可靠性**：依赖于 Kafka 的异步削峰和平稳消费，优先持久化落盘，再进行网络状态判断，保证消息 100% 留存。
- **解耦合**：消息的处理逻辑不再强耦合 WebSocket 层的即时反馈，离线和在线走相同的主干逻辑，只需在最后的发送末端进行分支阻断。
- **缓存加速**：通过在 Redis 缓存中同步维护消息列表 (`Cache-Aside` 模式)，有效应对客户端刚上线时的大量离线消息拉取请求（防止缓存击穿和数据库雪崩）。

## 3. 未来扩展（TODO）

根据现有的产品规划，当前的系统纯粹依赖**站内信的拉取机制**，暂时没有针对离线应用层的“第三方手机弹窗推送”。后续的演进可以考虑：
- **集成第三方推送服务（Push Notification）**：如 APNs（苹果）、FCM（谷歌）、华为/小米/机型原生推送等。
- **具体方向**：在判断用户离线（即 `Clients.Load` 失败）时，向一个专门负责离线推送的第三方消息列队/组件发送指令，唤醒用户手机通知栏。
