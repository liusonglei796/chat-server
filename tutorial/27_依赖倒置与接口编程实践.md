# 依赖倒置与接口编程实践

在 KamaChat 的 `server.go` 中，有一段非常经典的代码设计，完美诠释了**依赖倒置原则 (Dependency Inversion Principle)**。

```go
type ChatServer struct {
    // ...
    // Broker 消息代理接口（抽象层）
    Broker MessageBroker
}
```

很多初学者会问："为什么这里要用 `Broker MessageBroker` (接口)，而不是 `Broker *ChannelBroker` (具体结构体)？"

本文将深入剖析这种设计背后的三个核心理由。

## 1. 核心理由：多态性 (Polymorphism)

这是最直接的业务需求。我们的聊天系统支持两种运行模式：
1.  **单机模式**：使用 `ChannelBroker`，基于 Go Channel 做内存转发。
2.  **集群模式**：使用 `KafkaBroker`，基于 Kafka 做分布式转发。

如果使用结构体，你必须写死某一种实现：

```go
// ❌ 错误示范：耦合了具体实现
type ChatServer struct {
    Broker *ChannelBroker  // 完蛋，Kafka 模式用不上了
}
```

如果使用接口，`ChatServer` 就不需要关心具体是谁在干活：

```go
// ✅ 正确示范：面向接口编程
type ChatServer struct {
    Broker MessageBroker   // 我不管你是谁，只要能 Publish 就行
}

// 启动时动态注入
if config.Mode == "kafka" {
    server.Broker = NewKafkaBroker()
} else {
    server.Broker = NewChannelBroker()
}
```

这就是**“拔插式设计”**。`ChatServer` 就像一台电脑，`MessageBroker` 是 USB 接口，你可以插鼠标（ChannelBroker），也可以插键盘（KafkaBroker）。

## 2. 工程理由：解耦 (Decoupling)

在分层架构中，**上层模块不应该依赖下层模块的实现细节**。

- `ChatServer` 属于 **Service 层**（业务逻辑）。
- `ChannelBroker/KafkaBroker` 属于 **Infrastructure 层**（基础设施）。

如果 `ChatServer` 直接引用了 `KafkaBroker`，那么业务代码就和 Kafka 绑定死了。万一哪天你想把 Kafka 换成 RabbitMQ 或 Pulsar，你的 `ChatServer` 代码就得重写。

使用接口后，`ChatServer` 只依赖 `MessageBroker` 这个**抽象协议**。无论底层设施怎么变，只要新组件实现了这个接口，业务代码一行都不用改。

## 3. 测试理由：可测试性 (Testability)

这是高手和新手的生与死之界。

假设你要测试 `ChatServer` 的逻辑，如果它绑定了 `KafkaBroker`，那么你跑单元测试时必须：
1. 本地起一个 Zookeeper。
2. 本地起一个 Kafka。
3. 如果连不上，测试直接挂掉。

这简直是噩梦。但如果使用接口，你可以轻松造一个**假的 (Mock)**：

```go
// 假的 Broker，专门骗 ChatServer 做测试用
type MockBroker struct{}

func (m *MockBroker) Publish(ctx context.Context, msg []byte) error {
    fmt.Println("假装发送成功了")
    return nil
}

func TestChatServer(t *testing.T) {
    server := ChatServer{
        Broker: &MockBroker{}, // 注入假对象
    }
    server.Run() // 跑得飞快，不需要任何真实环境
}
```

## 总结

在 Go 语言开发中，遵循以下原则能让你的代码更健壮：

1.  **多用接口，少用具体类型**：特别是在核心业务层。
2.  **依赖注入**：不要在结构体内部 `New` 用于依赖的对象，而是通过参数传进来（Inject）。
3.  **面向协议设计**：关注“它能做什么”（Has-a method），而不是“它是谁”（Is-a struct）。
